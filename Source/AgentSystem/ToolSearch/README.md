# ToolSearch

ToolSearch indexes registered Dynamic Tools and records completed routing scenarios in MemOS. A scenario carries the resolved state card, selected tools, active Skills, and grounded execution outcome. Conversation memory and routing memory therefore share one durable semantic authority; there is no separate ToolLearning queue, keyword extractor, or Skill-learning database.

MCP service metadata is indexed before `tools/list`, so missing configuration does not erase the service from discovery. A compact `services` card reports a selected service's `id`, producer title/description, and `availability`; it is not a callable tool or a substitute contract. Cached tool candidates expose non-ready states in `availability[toolName]`: `unverified`, `needs_input` with exact input IDs, or `unavailable` with a reason. Services and strong matches are retained as evidence outside the uncertain-candidate budget. ToolDescribe can show an unavailable contract but does not confirm it; ToolLoad cannot expose it, and capability reuse cannot hide a newly relevant unavailable service. Model-facing availability contains no input values.

An immutable root grant can include installed MCP service IDs and package revisions under the registered-catalog policy. Current tools are resolved from that scope after deferred discovery, rather than intersected with the turn's earlier name snapshot. Explicit tool-name ceilings do not gain service scopes. Newly discovered BAML tools are registered with Pi before exposure updates; Native confirms the real contract and calls it through the existing fixed ToolCall bridge.

Bootstrap System Tools are provider-resident and called directly. They are deliberately excluded from ToolSearch's lexical index, semantic catalog, and discovery result so a model cannot rediscover a tool it already has and incorrectly route it through `ToolCall`. Dynamic tools remain discoverable through the immutable authorization grant. Search documents are derived from descriptions, authoritative contracts, capabilities, tags, examples, resource declarations, and discovery sources; when a standard MCP registration has no explicit source list, the same document builder derives one from its registration provenance, without a server-name mapping. The index never scans extension directories or contains a hard-coded capability list.

Retrieval is a bounded multi-channel operation. BM25 supplies lexical recall, local `fuzzysort` adds typo- and abbreviation-tolerant matching over declared identifiers, and `ternlight-mini-cn` supplies local cross-language semantic candidates. The channels are fused before deterministic reranking, then a BIC change-point model partitions each query's score curve into `match`, `maybe`, and omitted bands without a fixed result count or calibrated cosine floor. A `match` additionally needs a unique proof derived from producer declarations (complete example, identity, complete coverage, composite capability facets, or resource contract), or must be the single isolated semantic leader with no lexical shortcut. Shared proof keys are automatically downgraded to `maybe`, so duplicate aliases and generic operation phrases remain visible without becoming implicit execution authority. A flat or ambiguous frontier is disclosed by name; the weaker tail and any candidates that cannot fit the active token budget are grouped as `more` by the sources to which those actual withheld candidates belong. The projection evaluates named candidates and those source roll-ups together, so verbose `maybe` descriptions cannot starve the model of the remaining `+N` capability signal. `more` is never the full inventory of a source that happened to contain one hit. A resource declaration proves that a tool accepts a supplied path or URL, but it does not suppress other operations in the same compound request: those remain `maybe` candidates unless they independently have unique direct evidence. The pipeline never injects a hard-coded synonym list and never exposes retrieval strategy choices to the model. ToolSearch never infers resource syntax from a capability-ID spelling. The builtin `ternlight-mini-cn` client is not a translation service: package-declared or tool-declared localized aliases remain the authoritative cross-language retrieval contract for an MCP tool whose canonical description is in another language. Localization keys are matched by normalized MCP identity and validated against the discovered tool list; the host does not maintain server-specific alias tables. Once MCP discovery settles the catalog, the local engine, lexical index, and primary document vectors are prepared as a cooperative, cancellable background task; vectors are persisted under the workspace cache. Each capability's short identity, tags, facets, and declared aliases form a separate primary semantic view, while longer intent and contract views are expanded only for candidates whose primary evidence is ambiguous. A foreground semantic query can preempt derived work; completed vectors remain reusable by content identity. Tool and Skill routing use the same lexical, embedding, and document-cache services. An unavailable embedding channel is observable but does not fail lexical retrieval; an aborted turn still propagates cancellation.

`ToolSearch.Fuzzy` owns local typo recovery (`Enabled`, `MinScore`) and has no model or network dependency. `ToolSearch.Embedding.Enabled` controls the semantic channel; it has no score floor, language selector, provider selector, or candidate-expansion threshold. When enabled, the runtime always uses the builtin local `ternlight-mini-cn` encoder. It is offline and processes Chinese, English, and mixed queries in the same retrieval path; no query-character branch can disable it. There is no remote embedding or rerank transport configuration. Remote reranking is intentionally not supported. If the local semantic engine fails, the result remains explicit through `diagnostics=["semantic_unavailable"]` and the deterministic channels still return their evidence; this is an observable degraded result, not an unreported ranking fallback. Cancellation still propagates as cancellation. `ToolSearch.Rerank` controls the local deterministic feature reranker, while the query's own score curve and declaration-proof analysis determine disclosure.

Scenario recording happens at the completed-turn boundary. Every normally completed turn with a resolved state card is projected into MemOS; tool calls, active Skills, and execution assessment enrich that scene when present. Tool and Skill evidence are ranked from the same scenario records with time decay and current Skill revisions; static declarations remain authoritative. There is no detached learning result state, repair loop, or second attribution path.

Safety is enforced at execution time by approval, OPA, resource projection, and the selected execution environment. Search ranking must not duplicate those policies.

## Meta-tool contract

Each turn begins with only registry-declared `Bootstrap` tools exposed. A package may constrain a planner-only management contract through `planningModes`; otherwise its contract is portable. Dynamic tools remain authorized by the root command but do not enlarge the Native provider schema. Native planning invokes them through the fixed `ToolCall` bridge after `ToolDescribe`; BAML planning retains explicit session loading because its planner consumes the exposure snapshot.

The turn-preparation path never preloads Dynamic tools by matching the raw user message. A pinned/reused capability or an interaction-required tool can already be visible, but ordinary discovery is an explicit model decision through the protocol below. This keeps the first request independent of catalog size, prevents an approximate embedding match from becoming an implicit tool choice, and preserves a stable provider-tool prefix.

| Tool                      | Responsibility                                                                                                                                            | Session effect                                 |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `ToolSearch`              | Returns a compact discovery card: `match` names are actionable, `maybe` names need relevance judgment, and `more` folds the weak tail by declared source. | None                                           |
| `ToolDescribe`            | Returns a compact TypeScript-like contract for Dynamic tools; `direct` marks an already-native Bootstrap tool that must be called directly.               | Confirms Dynamic contract for native execution |
| `ToolCall`\*              | Native-only fixed bridge that unwraps an exact dynamic tool name, contract revision, and arguments before normal authorization.                           | Does not change the provider tool schema       |
| `ToolLoad` / `ToolUnload` | Adds or removes authorized dynamic tools by exact name for BAML planning.                                                                                 | Updates BAML's exposure snapshot               |

\* `ToolCall` is the only entry here that is not a `System/Extensions/**/tools/*.tool.json` contract: `AgentPiNativeToolBridge` injects the name into the native provider schema at runtime. The other four are registry-declared and searchable; `ToolCall` is `Bootstrap`-like in effect but is not discoverable metadata.

`ToolSearch` accepts only the original task query and returns evidence-backed Dynamic candidates in deterministic score order. Its wire is deliberately shallow JSON with positional tuples: `match=[[toolName,description,state?]]`, `maybe=[[toolName,description]]`, and `more=[[sourceId,sourceName,omittedToolCount]]`. `match` is the actionable proof tier and is never removed for the uncertain-candidate token budget; `maybe` and `more` share that budget. `more` is a coverage hint derived from the actual withheld candidates: it says that `omittedToolCount` relevant candidates came from `sourceId`/`sourceName`, but `sourceName` is not a callable tool and no source-wide inventory is implied. Use `ToolSearch` again to retrieve concrete names. `description` is producer-authored `search.Summary`, or, when a summary is absent, the de-duplicated capability `Description` declarations. A presentation title and tool name never silently replace that semantic description; incomplete Dynamic declarations fail during registry commit instead of waiting for the first search. Full parameter schemas, effects, and provenance remain behind `ToolDescribe`, so broad retrieval never repeats nested JSON contracts. The host combines lexical, fuzzy, semantic, resource, and completed-scenario evidence before projecting this card; the model never selects a retrieval mode or receives a zero-confidence full inventory during normal routing. When no candidate can be returned, the card includes `status="empty"` and a structured `reason` such as `no_available_tools`, `not_authorized`, or `no_match`; an unavailable optional embedding channel is reported in `diagnostics` while lexical retrieval remains usable. A catalog refresh during retrieval is retried against a coherent immutable snapshot; if it continues changing, the card is empty with `reason="catalog_changed"` and the current `catalogRevision`. Management UI reads registry metadata directly; it does not invoke an alternate ToolSearch mode. `ToolSearch` does not publish contracts or load candidates. `ToolDescribe` returns `tools=[[toolName,title,"use: ...\nargs: ...\nreturns: ...\nboundary: ..."]]`: JSON preserves fixed routing, while the selected contract is a compact TypeScript-like text block instead of JSON-inside-JSON. It never executes or loads a tool, but confirms the delivered contract digest for the fixed native bridge. The underlying JSON Schema remains authoritative for host validation. `ToolCall` accepts only Dynamic tools already present in the immutable authorization grant, rejects stale contract revisions, and requires a current `ToolDescribe` confirmation or revalidated reusable-capability evidence. `ToolLoad` and `ToolUnload` accept the optional `catalogRevision` from the discovery card and return `catalogStatus="stale"` without mutating exposure when it no longer matches; neither can expand the immutable authorization grant. `ToolUnload` preserves every Bootstrap tool. Skill recommendations remain contextual hints; they neither alter ranking invisibly nor bypass the active planning protocol.

## Confirmed capability reuse

The host keeps a bounded capability-evidence record per durable session and `logicalCacheScope`. The record is populated only after a successful Dynamic-tool invocation and is revalidated against the current catalog identity and contract digest before use. A visible tool is therefore still returned by `ToolSearch` with explicit `exposure` state; visibility is not treated as contract confirmation.

Only declarations that are read-only, effect-free/read-state, and approval-safe are eligible for automatic argument reuse. Tools that write state, touch the network, change workspace state, send messages, or require approval may retain confirmed evidence for diagnostics, but their old arguments are never silently replayed. When automatic reuse is valid, the same immutable capability list is passed through preparation, volatile prompt context, ToolSearch, preflight, resource claims, and execution. Explicit arguments supplied by the model always override remembered values.

Index or extension refreshes do not clear this evidence. A changed catalog or contract naturally invalidates it on the next lookup, which preserves stable prompt/provider cache prefixes while avoiding unrelated cache cold starts. A reused ToolSearch result is not written as a new scenario because no new completed execution occurred.

## Cache identity and invalidation

Capability indexes and embeddings are content-addressed, not revision-label-addressed. The catalog identity is a canonical hash of each document's stable ID, kind, declared revision, semantic inputs, and complete `semanticText`. Each capability derives structural semantic inputs from its actual title, intent, examples, and contract fields; the index starts with the primary input and expands to the other views only when the returned evidence is weak or ambiguous. It scores the strongest view without a language-specific branch. The embedding identity is a canonical hash of `(embedding model, document ID, input ID, SHA-256(input text))`. Changing only a description, example, capability, parameter summary, owner text, or embedding model therefore invalidates the affected vector even when a producer forgot to bump its revision string.

The shared embedding cache is a bounded `AgentLruCache`. Its capacity scales with the active catalog, accesses refresh recency, and catalog refresh removes identities that are no longer reachable. Query vectors are not mixed into the document cache. A failed embedding channel remains observable while independently computed lexical evidence stays available; cancellation is never converted into an empty-success result. For a multi-view capability, the primary semantic view first ranks the full catalog. Only primary candidates inside the configured confidence band, bounded by the existing rerank candidate budget, receive auxiliary-view vectors on that foreground request. The embedding client declares its own bounded work unit, and the index yields between units, so background catalog preparation remains preemptible without paying one IPC round-trip per document.

MCP `notifications/tools/list_changed` is handled by the MCP SDK's negotiated list-change support. Refreshed declarations pass the same JSON Schema validation as startup discovery, replace one server owner transactionally, and invalidate the search index. Invalid updates leave the previous catalog installed.
