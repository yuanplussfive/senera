# 会话消息与渠道交付

主控台、桌面端、手机端和渠道共用 Session 输入入口。Native 与 BAML
只改变工具调用方式，不改变接收、排队与交付规则。

## 输入

渠道先将带原生消息或事件 ID 的输入写入 `channel_ingress`，再解析附件。
记录保留当时的目标会话，重复投递或重启恢复不能把旧消息路由到 `/new`
之后的会话。附件解析失败保留错误和原输入；未完成的导入重连后恢复。
请求头与平台凭据不入库，成功接收后移除重复的附件和原生消息段载荷。
没有 Agent 参与的群聊活动仍进入可查询历史。

新任务的用户消息、运行记录和启动事件先一起提交，再返回接收结果；
`acceptMessage` 不等待模型完成，`submitMessage` 可等待任务终态。
存储提交失败必须拒绝接收，不能让发送方误以为消息已保存。

运行期间的补充消息先写入会话数据库的 `session_inputs`，与用户消息历史
一起提交，再发布 `session.message.queued`。相同请求 ID 只能对应同一内容。
Pi 句柄尚未创建、任务正在收尾或取消时，接收与调度仍分开处理。

`steer` 在安全的模型边界加入当前任务，`follow_up` 等当前 Agent 轮次准备
结束时加入。待处理消息按接收顺序组成完整输入，受当前模型可用预算限制；
未选中的消息保留在队列，不能截断或假装交付。附件复用正常上传资源和图像
归一化服务。

状态依次为 `pending`、`delivered`、终态 `completed | failed | cancelled`。
`delivered` 表示已进入 Pi 的用户输入，不表示供应商成功响应、任务成功完成
或用户已经读到回复。前端使用宿主状态，其他客户端也从事件获得完整用户消息。

显式停止取消当前任务尚未消费的补充消息。服务器退出保留未消费输入；重启
先核对 Pi 原生记录，避免在提交输入与保存回执之间崩溃后重复执行。已经进入
旧任务的输入使用旧任务的终态，不自动重放工具副作用。尚未启动过独立任务的
未消费输入，在对应界面及当前权限可用后启动新任务。如果这个恢复任务已经
启动，但缺少原生输入回执，则显示明确失败并保留消息，交由用户决定是否重试；
不能仅凭回执缺失就推断没有执行过工具。主动删除会话或历史也会移除所属输入。

QQ 的持久事件收件箱在相同边界提供新消息，保留独立的历史游标与原生消息
ID；自行发言、当前任务产生的活动不会再次触发自己。等待条件、成员权限、
已撤回消息和 `/new` 的会话边界继续生效。

## 身份与对话事项

宿主在渠道适配器边界解析发言人，持久化 UUID 和短引用。原生账号是带认证来源的绑定：
官方 QQ 按 AppID 隔离 OpenID，Telegram 和 Discord 使用各自服务的账号空间；本地
Senera QQ 的操作者由宿主明确关联到工作区主人。昵称、消息正文和模型参数不能建立
跨账号绑定，短引用也不是登录凭据。收件箱保留每条消息自己的发言人。
官方 QQ 的会话、收件箱与交付同时按 AppID 分区；无法证明来源的旧会话保留在
历史存储中，不自动关联到当前应用，也不恢复其待发送消息。

QQ 的 `ChannelUpdateConversation` 将已观察到的消息关联为独立请求、当前事项的补充
或旁观消息。事项保存所有者、参与者、状态、下一步和可选回访时间；已读游标与事项
完成状态分开。修改需要当前 revision，同一工具调用重放返回原回执。原始消息仍只
保存在事件收件箱；liveContext 投影有预算的未完成事项，完整清单可按需读取。

模型决定话题关联、是否等补充、引用方式、表情和表达长度。宿主验证消息归属、版本
和当前渠道权限，串行调度待办、持久等待与交付。独立请求按登记顺序获得评估机会，
同一事项版本只安排一次评估；新消息仍通过原收件箱保留。带 taskId 的发送和等待
使用该事项的参与者范围，已归类的旁观活动不阻塞交付。取消事项需要所有者的新消息。

回访到期只触发重新评估，使用时间唤醒语义，不重复投递旧附件或把旧问题当成新指令。
暂停成员保留事项并撤销当前运行能力；`/stop` 停止当前工作和待续回访，`/new` 与删除
会话清理对应事项。日常交流不强制登记任务，也不会由宿主合成预回复或表情。

## 回复交付

模型先确认较长的任务，在有真实进展时说明阶段结果，最后交付结果。短答
和群聊不强制产生固定数量的消息。支持编辑的平台沿用节流预览；不支持编辑
的平台发送完整阶段消息。主控台记录、打字状态和渠道发言互不冒充。

所有持久回复和显式文字、媒体发送通过同一个 `AgentChannelDelivery`。
显式文字发送与引用回复统一接收 `messages: string[]`，每次 1～3 条；默认只发
一条完整消息，需要独立气泡时再拆分。引用和原生 @ 只作用于第一条，平台的
被动回复授权仍覆盖整批。文字发送单独执行，等待回执后再决定是否继续。
每条发送前重新检查收件箱、事项与权限，遇到新活动暂停剩余消息；取消或失败
同样停止。`messageIds` 按输入顺序保留已确认成功的回执，即使随后历史写入失败
也不丢弃。未确认的交付需核对失败码，`delivery_unknown` 不允许盲目重发。

每个传输片段在 `channel_outbox` 保存身份、内容、尝试次数和平台回执；工具
调用和回复渲染提供稳定身份。未发送片段重连后恢复，发送前重新检查权限。
已成功片段返回原回执。重启时仍处于 `sending` 的片段记为 `uncertain`，
通过日志报告 `delivery_unknown`，不自动重发。
网络中断且平台是否接收未知时也采用同一规则。存储故障报告
`storage_failed`，不将其伪装成平台拒绝，也不触发重复发送或恢复重试循环。

平台回执只能证明平台接收，不能证明用户已读。没有原生幂等接口的平台无法
提供跨进程、跨网络的严格一次发送保证。临时预览与打字状态是瞬时展示，
不进入持久交付队列。
