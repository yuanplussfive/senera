# 图标像素相位

这份文档解释一件事：**为什么同一套 `strokeWidth` 的图标，看起来粗细不一样**，以及哪些做法能解决、哪些不能。

适用场景：新增 `AppIcon` 语义、调整图标尺寸、编写窗口栏或其它需要精确笔画重量的控件。通用图标规范见 [../AGENTS.md](../../Frontend/AGENTS.md) 的「图标治理」一节。

## 1. 现象

`AppIcon` 用 24 单位画布（`viewBox="0 0 24 24"`），默认 `size=16`、`strokeWidth=1.75`。绘制时整体缩放到渲染尺寸，于是笔画落在像素网格的什么位置取决于缩放比例。

一条与像素轴对齐的笔画，如果笔画覆盖区间没有正好压满某一整行像素，就会摊到两行上、各画一部分透明度：

- 落在整数像素**中心**的笔画（Heroicons 的写法，例如 `M5 12h14`）→ 摊到两行；
- 落在像素**边界**上的笔画 → 正好填满一行。

两种情况的名义 `stroke-width` 完全相同，视觉上却一个偏细偏灰、一个饱满。这是**相位差**，不是宽度差。

在 16px / 1 倍屏下，`strokeWidth=1.75` 实际只画 **1.167 个设备像素**：横线（整数单位）读出 0.583 的浓度，方框（0.25 / 0.75 单位）读出 1.000。这就是「最小化的横线比最大化方框细」的成因。

## 2. 度量

`Scripts/AuditAppIconStrokePhase.mjs` 把上面这件事量化。对每条轴向直线笔画：

```
peak = 该笔画在每个像素行上的最大重叠长度
concentration = peak / min(stroke_px, 1)
```

除以 `min(stroke_px, 1)` 是为了让不同尺寸可比：宽于 1 像素的笔画可以靠压满一行达到 `peak = 1`，窄于 1 像素的笔画做不到（上限就是 `stroke_px`）。除完都落在 0..1，**1 表示「按名义粗细读出来」**。

只统计轴向直线（`H`/`V`/`L` 段、`line`、`rect` 边）。对角线和曲线在任何合理宽度下都到不了满浓度，属于范围外，不做平均。

运行方式（`--tsconfig` 不能省：jsx 配置在 Frontend 里，缺了 tsx 会走 classic runtime 并抛错）：

```bash
npm run quality.icon-phase                          # 逐尺寸汇总
npm run quality.icon-phase -- --can-align           # 这个库在该尺寸下有没有可用相位
npm run quality.icon-phase -- --width-sweep         # 加粗能不能换来相位容忍
npm run quality.icon-phase -- --adaptive 2.0        # 每个尺寸重算宽度，恒定画 N 像素
npm run quality.icon-phase -- --usage               # 生产实际用到的尺寸分布
npm run quality.icon-phase -- --icon minus --all    # 单个图标的每一段细账
```

这个脚本是**诊断工具，不进 verify 门槛**：当前目录里 83 个有轴向直线的图标中，绝大多数在该尺寸下本就不对齐，改成硬性关卡只会产生噪音。它的用途是在改动前后跑一遍、对比数字。

## 3. 相位窗口

对宽度 `w`（设备像素）的笔画，能读满的笔画中心分数遵循一个**在 1 像素处反转**的规律：

- `w < 1`（细线）：覆盖区间不能跨越像素边界，必须整体落在某一行内 → 好的中心分数聚在 **0.5**，窗口宽度 `1 − w`。
- `w ≥ 1`：覆盖区间必须压满某一行，即区间内要包含一个整数 → 好的中心分数绕 **0** 分布，窗口宽度 `w − 1`。

所以细线只能在**两个像素边界之间**对齐，粗笔画只能在**像素中心**对齐。两者恰好相反。

**容忍度和重量是同一个旋钮**：窗口宽度就等于 `|w − 1|`。

推论（重要）：当 `w ≥ 2` 时窗口宽度 ≥ 1，一个完整周期内必然命中，**任何位置都不再敏感**。这是唯一一个与相位无关的宽度。

## 4. 实测结论

默认 `strokeWidth=1.75`，按生产尺寸逐项测（83 个有轴向直线的图标，全部笔画都对齐才算数）：

| 尺寸     | 设备像素(DPR 1) | 对齐          | 说明                           |
| -------- | --------------- | ------------- | ------------------------------ |
| 12px     | 0.875           | 9/83 (11%)    | 细线区，聚在 0.5 附近          |
| 13px     | 0.948           | 12/83 (14%)   | 在 1 像素附近，最敏感          |
| **14px** | **1.021**       | **0/83 (0%)** | 用量最大的尺寸，恰好落在最坏点 |
| 15px     | 1.094           | 14/83 (17%)   |                                |
| 16px     | 1.167           | 10/83 (12%)   | 默认尺寸                       |
| 18px     | 1.313           | 3/83 (4%)     |                                |
| 28px     | 2.042           | 83/83 (100%)  | `w ≥ 2`，与相位无关            |

**换尺寸不是杠杆。** 恒定画 1.0 设备像素（`--adaptive 1.0`）时 14px 是 0%、没有任何尺寸超过 16%；加到 1.5 像素也只有 17–47%。只有**恒定画满 2.0 设备像素**（`--adaptive 2.0`）在**每一个尺寸**上都达到 100%。

**加粗也不是免费午餐。** 12–16px 的 UI 图标画到 2 像素会明显过重；而 1.75 单位在 13–17px 这一档换算出来正好是 0.95–1.24 设备像素，是整张表里最坏的一段。

**库几何本身救不回来。** Heroicons 所有坐标都是整数单位，在 16px 和 24px 下**没有任何**整数单位落进相位窗口；14px 下 12 个里只有 1 个。

**高分屏会掩盖问题。** 同一个 CSS 尺寸，设备像素随缩放比例翻倍：16px 在 DPR 1 下 10/83，DPR 1.5 下 17/83，DPR 2 下 83/83（2.333 设备像素）。在 2 倍屏上看着没问题，不代表 1 倍屏上没问题。

## 5. 可用做法

### 5.1 通用图标：接受默认，不要为此改尺寸

`AppIcon` 的 112 个图标走库几何，12–16px 下无法逐一对齐，**这是库的属性而不是缺陷**。不要为了「相位好看」去给某个图标换一个奇数尺寸——数据上那样做没有收益，而且会把尺寸散得更碎（当前已经是 12 个尺寸）。

需要复查视觉时，用 `AppIcon.stories.tsx` 的 `ProductionSizes` Story 在真实尺寸下并排看笔画灰度，而不是看形状。

### 5.2 需要精确重量的控件：自己画几何

当一组控件必须在同一尺寸下笔画完全一致（窗口栏最小化 / 最大化 / 关闭就是这种情况），不要去调 `strokeWidth` 数值，而是**把坐标画在能对齐的网格上**。

`Frontend/src/shared/ui/WindowControlGlyph.tsx` 是范例：所有中心线落在 **0.75 单位网格**上（`0.75 × 16/24 = 0.5px`），`strokeWidth = 1.5` 单位在 16px 下正好画 **1.0 像素**，压满一行。在 DPR 1、1.25、1.5、1.75、2、3 下三个控件的浓度都是 1.000。

这类专用 glyph 与 `AppIcon` 并列、不塞进它的目录：`AppIcon` 是功能代码共用的语义词表，而窗口栏这几个形状的存在理由就是上面的像素相位。功能代码继续用 `AppIcon`。

### 5.3 新写图标时的自检

1. 笔画是否需要在目标尺寸下读出**精确**重量？不需要 → 用 `AppIcon` 默认值，别管相位。
2. 需要 → 自己画几何，中心线放在 `(size / 24) × 0.75` 这类能落在半像素边界的位置上；先确认在该尺寸下 `w ≥ 2` 或中心线正好压边界。
3. 改完在**目标缩放比例**下复查。用 `npm run quality.icon-phase -- --adaptive <px>` 验证，而不是只在当前显示器上看。
4. 补一条行为断言（例如三个控件共享同一 `stroke-width` 和 `viewBox`），别只靠肉眼。

## 6. 为什么不是「统一尺寸」

曾经考虑过定一份允许尺寸清单来规避相位差。实测否掉了：

- 尺寸不是杠杆（第 4 节 `--adaptive` 数据），换尺寸换不来对齐；
- 唯一全尺寸干净的做法是恒定画 2 设备像素，在 12–16px 档过重；
- 落地这份清单意味着改动 314 处 `<AppIcon>` 元素，而它对缺陷没有作用。

有效的组合是另外两件事：**让缺陷在 Story 里可见**（`ProductionSizes` 按真实尺寸铺开），加上**这份可重跑的度量**。AI 下次写图标时至少能看见问题、能算出数字，而不是靠猜。
